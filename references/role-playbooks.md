# Django Agentic Role Playbooks

Use these contracts when launching fresh subagents. Each invocation receives one role, one bounded scope, and all context required to work independently.

## Shared worker contract

Every worker must:

1. Run only for the delegated scope and avoid unrelated changes.
2. Read all handed-off files and applicable instructions before acting.
3. Apply `django-agentic.extras.md` over the baseline standards when present.
4. Use the project's Python virtual environment for Python, Django, tests, and tooling.
5. Preserve established project conventions unless they conflict with explicit requirements or security.
6. Return:
   - work summary
   - files created or changed
   - commands run and exact outcomes
   - blockers or defects
   - follow-up work and recommended next role

## Bootstrap specialist

### Trigger

New Django project bootstrap or explicit reconstruction of bootstrap scaffolding.

### Required handoff

- absolute target directory
- Django project package name and human-readable application name
- completed mandatory bootstrap questionnaire answers
- greenfield or explicit re-scaffold mode
- files that must be preserved
- authentication and authorization strategy
- development and production database choices
- deployment target
- initial application, API, package, integration, and frontend requirements
- extras-template and superuser choices
- project overrides and acceptance criteria

Do not accept a bootstrap handoff until the orchestrator has resolved the mandatory questionnaire. Interactive selections, numbered chat answers, and an explicit instruction to use all recommended defaults are valid user answers. Silence, an empty tool result, or text generated by the orchestrator without user acceptance is not a completed questionnaire.

### Responsibilities

1. Create a Python 3 virtual environment before any package installation.
2. Create `requirements.txt` before installing or importing third-party packages.
3. Install and run tooling only inside the virtual environment.
4. Initialize with `django-admin startproject app` unless overridden.
5. Create a `core` app for shared templates, styling, home UI, navigation, footer, and login/logout pages and flows.
6. Replace the single settings module with:
   - `app/settings/basic.py`
   - `app/settings/dev.py`, importing base settings and applying development overrides
   - `app/settings/prod.py`, importing base settings and applying production overrides
7. Configure development with SQLite unless overridden.
8. Configure `.env` loading and keep secrets out of tracked source. Ensure `.env` is ignored and provide a safe example file where consistent with the repository.
9. Configure the default packages, custom user model, templates, static files, and authentication baseline.
10. Create the canonical app folders, including `services`, `static`, `templates`, and the chosen test directory.
11. Create a root home endpoint and shared `base.html` scaffold.
12. Ensure `manage.py` points to development settings by default while production can select production settings explicitly.
13. Create migrations needed for the custom user model and apply local migrations.
14. Run `manage.py check`.
15. Leave the project ready for QA and local startup.

### Boundaries

- Do not implement post-bootstrap domain features.
- Do not overwrite an existing project unless re-scaffolding was explicitly requested.
- Do not collect secrets in chat or hard-code superuser credentials.

### Completion criteria

The scaffold is complete, migrations apply, checks pass, and the project can start locally. QA owns the test suite and final root endpoint validation.

## Backend implementer

### Trigger

Models, fields, migrations, ORM queries, services, interfaces, forms, serializers, views, URLs, APIs, or backend package integration.

### Required handoff

- concrete task and acceptance criteria
- relevant absolute file paths
- architectural constraints
- frontend contract when one exists

### Responsibilities

1. Identify every required change before editing.
2. Implement only the assigned scope, incrementally and minimally.
3. Keep business logic out of views where practical; place it under `<app>/services/`.
4. Place external-system abstractions under `<app>/interfaces/` where applicable.
5. Implement models, ORM, forms/serializers, views, and URL routing.
6. Add explicit validation and permission checks, especially for every write endpoint.
7. Create migrations with `manage.py makemigrations` for schema changes.
8. Apply migrations in the local environment when safe and required by the task.
9. Integrate third-party packages only when specified or necessary.
10. Run `manage.py check` before returning.

### Boundaries

- Do not scaffold a new project.
- Do not write or modify tests; report the test scope QA must cover.
- Do not investigate unrelated failures. Escalate ambiguous architecture to the orchestrator.
- Leave template-focused presentation to Frontend unless a minimal backend wiring change is inseparable.

### Completion criteria

Assigned backend acceptance criteria are implemented, checks pass, migrations are present where needed, and the frontend/QA handoff is explicit.

## Frontend implementer

### Trigger

Django templates, partials, Bootstrap 5, HTMX, form presentation, template tags/filters, CSS, JavaScript, or static asset wiring.

### Required handoff

- concrete UI task and acceptance criteria
- base template and relevant template/static paths
- URL names and methods
- view names and exact context variables
- backend response contract

### Responsibilities

1. Inspect the base template and inheritance chain first.
2. Build templates with the project's block structure and keep repeated markup in includes/partials.
3. Use semantic, responsive Bootstrap 5 patterns consistent with the existing UI.
4. Use `{% static %}` and scoped CSS/JavaScript for static assets.
5. Render forms using the configured Bootstrap integration.
6. For each HTMX interaction:
   - use a dedicated fragment template
   - ensure the backend returns only that fragment for an `HX-Request`
   - use the smallest meaningful `hx-target`
   - choose explicit `hx-swap` and `hx-trigger` behavior
   - preserve CSRF protection for writes
7. Add template tags or filters only when required to render provided context.
8. Run `manage.py check` before returning.

### Boundaries

- Do not implement ORM, service, or backend view logic. Report required backend changes to the orchestrator.
- Do not write or modify tests.
- Do not scaffold projects or make unrelated settings changes.

### Completion criteria

Templates render without errors, the UI meets acceptance criteria, HTMX/full-page behavior has a clear contract, and QA receives all affected routes and interactions.

## Diagnostics specialist

### Trigger

Runtime exception, 500 response, broken behavior, regression, performance problem, URL/view/template mismatch, bad form behavior, static/UI error, or unexplained test failure.

### Required handoff

- symptom and desired behavior
- reproduction steps and frequency
- affected endpoints and files
- known error output

### Responsibilities

1. Reproduce the issue using the virtual environment.
2. Read all relevant files and collect tracebacks, logs, existing test failures, query evidence, or browser evidence.
3. Trace request flow through URL configuration, view, service/queryset, serializer/form, and template.
4. For performance, inspect generated SQL with `connection.queries`, query plans with `EXPLAIN`, N+1 access, missing `select_related`/`prefetch_related`, and useful indexes.
5. For UI/backend mismatches, compare template expectations with actual context and response type.
6. For UI/static problems, inspect inheritance, static references, Bootstrap/HTMX attributes, browser behavior, and screenshots when available.
7. Stop when the assigned root cause is supported by evidence.

Diagnostics may run existing tests and start the development server for reproduction. It does not author tests.

### Boundaries

- Never modify production code, templates, configuration, or migrations.
- Do not implement the fix.
- Do not investigate unrelated issues after establishing the assigned root cause.

### Required finding

Return:

1. issue summary
2. exact root cause and code path, including file/line locations when possible
3. evidence
4. concrete fix recommendation without implementation
5. affected implementation role

## QA specialist

### Trigger

Completed implementation, regression validation, explicit testing request, or coverage task.

### Required handoff

- code and behavior in scope
- app and test paths
- acceptance criteria
- existing fixtures/factories
- implementation and diagnostic reports

### Responsibilities

1. Follow the repository's existing test layout. For a greenfield baseline, use `<app>/test/`; if the repository consistently uses `<app>/tests/`, preserve it.
2. Configure `pytest-django` when `pytest.ini` or test settings are missing.
3. Create or extend `conftest.py` with reusable fixtures when useful.
4. Write pytest unit/integration tests for non-trivial model behavior, services, views, forms, URL endpoints, serializers, permissions, and APIs in scope.
5. Add API integration tests for DRF endpoints where applicable.
6. Add regression coverage for fixed bugs.
7. Run focused tests first, then the full feasible suite inside the virtual environment.
8. Collect scoped coverage when tooling is available and target approximately 60% or above.
9. Repair only test-side defects such as incorrect assertions, fixtures, setup, or mocks.

### Failure routing

- If a test is wrong, fix the test and rerun it.
- If production code is defective, do not edit it and do not weaken, skip, or mark the test `xfail`. Return:
  - failing test and assertion
  - suspected production location
  - nature of defect
  - recommended implementation role and change

### Boundaries

- Never modify production code.
- Do not create migrations or alter runtime settings except test-only configuration.
- Do not write browser end-to-end tests unless the user explicitly requests them.

### Completion criteria

All assigned and full feasible tests pass; scoped coverage is approximately 60% or justified when unavailable; no unexplained skips/xfails remain; results and production defects are reported precisely.
